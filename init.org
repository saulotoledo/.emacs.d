* About
This is my personal Emacs configuration, written and maintained in Org mode.

It contains my preferred packages, UI tweaks, and programming workflow. I tangle
and load the relevant Emacs Lisp directly from this file, keeping the Org source
as the single source of truth for my setup. (Learn more at the [[https://orgmode.org][Org mode
website]].)

My configuration uses a layered structure inspired by [[https://www.spacemacs.org/][Spacemacs]] and [[https://docs.doomemacs.org/][Doom Emacs]].
While those are great out-of-the-box distributions, I prefer building my own
system from scratch to understand how everything works under the hood.

The config generates three separate files: ~early-init.el~, ~setup.sh~, and
~init.el~ -- with the vast majority of the code tangled into ~init.el~ for
speed. Where Spacemacs resolves layer dependencies dynamically at runtime and
Doom uses =straight.el= to manage its modules, this setup borrows the layer
concept from Spacemacs while adopting Doom's focus on fast startup performance.

* Architecture & Layer System
Before diving into the Emacs Lisp code, this section outlines how this
configuration is organized across layers and how files are tangled.

** Anatomy of a Layer
A layer is an abstraction over packages that bundles related tools, settings,
keybindings, and custom functions together. Each layer is defined in a
~README.org~ file under ~layers/<group-name>/<layer-name>/~ and contains four
standard sections:

- *Description:* A short introduction to the layer's purpose.
- *Emacs Configuration:* The packages, custom variables, and functions defined
  by the layer.
- *Keybindings:* Setup and quick-reference list of all keybindings introduced by
  the layer.
- *System Setup:* Shell script blocks tangled into ~setup.sh~ to automate the
  installation of external system dependencies (binaries, linters, fonts, etc.).

** Layer Priority System
Layers are loaded in a deterministic order based on a priority system:

- By default, all layers have a priority of *100*. Ties are broken
  alphabetically.
- Adding a file named ~PRIORITY~ containing a number (e.g., ~0~) inside a
  group's root directory changes the default priority for that entire group.
- Adding ~#+LAYER_PRIORITY: x~ (where ~x~ is a number) inside a layer's
  ~README.org~ overrides the priority for that specific layer.

** The Build & Retangling Pipeline
Standard ~org-babel-tangle~ isn't enough for this setup because we distribute
code across multiple files using ~#+INCLUDE~ directives. When a build is
triggered, our custom discovery script in [[file:retangle.el][retangle.el]] executes the following
pipeline:

1. Refreshes [[file:layers/README.org][layers/README.org]] with updated ~#+INCLUDE~ blocks for every layer.
2. Resolves and expands all includes into a temporary buffer.
3. Tangles the code into ~init.el~, ~early-init.el~, and ~setup.sh~.
4. Optionally native-compiles ~init.el~ for speed (if ~gcc~ is installed).

*** How to Trigger a Retangle
You can trigger the retangling process in three ways:

- *Interactively:* Run ~M-x cfg-core/retangle-init~ (use a prefix argument to
  also native-compile).
- *Automatically:* Saving ~init.org~, [[file:setup-script.org][setup-script.org]], any layer ~README.org~
  (not ~layers/README.org~), or any ~layers/**/PRIORITY~ file triggers an
  ~after-save-hook~ that retangles and compiles automatically.
- *From a terminal:*

#+begin_src sh :tangle no
emacs --batch -Q -l ~/.emacs.d/retangle.el -f cfg-core/retangle-init
#+end_src

*Note:* Native compilation is not available from the terminal. Because ~emacs
--batch -Q~ skips package initialisation, ~native-compile~ cannot resolve the
packages that ~init.el~ requires at load time. Native compilation happens
automatically in the background the first time you open Emacs after a retangle
(triggered via ~run-with-idle-timer~).

* General Configuration

** Early Bootstrapping & Headers
We start by enabling [[https://www.gnu.org/software/emacs/manual/html_node/elisp/Lexical-Binding.html][lexical binding]] at the very top of our init files. Note
that we apply this to both =init.el= and =early-init.el=.

The =early-init.el= file was introduced in Emacs 27. If present, Emacs evaluates
it before initializing the package system or the GUI. This makes it the ideal
place to configure early startup optimizations and visual settings.

The =init.el= file is the standard Emacs initialization file where the bulk of
our configuration lives.

#+begin_src emacs-lisp
;;; init.el --- Personal Emacs configuration -*- lexical-binding: t; -*-
#+end_src

#+begin_src emacs-lisp :tangle early-init.el
;;; early-init.el --- Instructions loaded before the package system and GUI -*- lexical-binding: t; -*-
#+end_src

We adhere to common Emacs Lisp conventions by establishing clear headers for
file organization. This divides the generated files into two primary sections:

- =Commentary:= Provides a high-level, human-readable summary of the file's
  contents, organization, and purpose. It is the first thing a reader sees.
- =Code:= Marks the official starting point of the executable Emacs Lisp
  configuration. Everything following this header is active setup logic.

For the main file:

#+begin_src emacs-lisp
;;; Commentary:
;;;
;;; This file contains my personal Emacs configuration.
;;;
;;; Code:
#+end_src

For the early init file:

#+begin_src emacs-lisp :tangle early-init.el
;;; Commentary:
;;;
;;; This file contains instructions that must be loaded before the
;;; package system and the Emacs GUI.
;;;
;;; Code:
#+end_src

** Automatic Retangling Setup
We register an ~after-save-hook~ so that saving this file (or any layer file)
automatically re-evaluates and retangles the configuration.

The code from [[file:retangle.el][retangle.el]] is shown below:

#+begin_src emacs-lisp
(load (expand-file-name "retangle.el" user-emacs-directory) nil t)
(declare-function cfg-core/tangle-and-compile-init "retangle")
(add-hook 'after-save-hook #'cfg-core/tangle-and-compile-init)
#+end_src

** Core & Startup Settings
*** Faster Startup
A common and effective way to speed up Emacs startup is to defer garbage
collection and file-name handler processing during initialization. Garbage
collection can run frequently while Emacs is loading packages and configuration,
and ~file-name-handler-alist~ adds overhead to every file operation (for
example, Tramp checks). Both are useful during normal operation, but
unnecessarily slow down startup. The configuration below temporarily:

- Raises ~gc-cons-threshold~ to an extremely large value, effectively disabling
  garbage collection.
- Clears ~file-name-handler-alist~, eliminating file handler checks during
  initialization.

Once Emacs has completed its initial loading phase, the following restoration
steps occur:

- *Restore File Handlers (after-init-hook)*: The ~file-name-handler-alist~ is
  restored on ~after-init-hook~. This timing is critical because it executes
  before command-line files are visited but after your configuration is loaded.
  If this restoration were delayed until ~emacs-startup-hook~, files passed as
  arguments (e.g., =emacs foo.gpg=) would open before handlers are re-enabled.
  Consequently, EasyPG would fail to intercept the =.gpg= extension, leaving the
  buffer displaying raw ciphertext until manually reverted.
- *Restore Garbage Collection (~emacs-startup-hook~)*; GC thresholds are reset
  on ~emacs-startup-hook~. By deferring this until the very end of the startup
  sequence, Emacs avoids the performance penalty of frequent garbage collection
  during the intensive loading phase.
- *Suppress System Defaults (~inhibit-default-init~)*: Setting
  ~inhibit-default-init~ to non-nil prevents Emacs from loading the system-wide
  =default.el= library. This ensures that only your personal initialization file
  is processed, avoiding potential conflicts with site-specific customizations.

#+begin_src emacs-lisp :tangle early-init.el
(let ((file-name-handler-alist-old file-name-handler-alist))
  (add-hook 'after-init-hook
            (lambda ()
              (setq file-name-handler-alist file-name-handler-alist-old)))
  (add-hook 'emacs-startup-hook
            (lambda ()
              ;; Restore reasonable defaults after startup
              (setq gc-cons-threshold (* 100 1024 1024)) ;; 100 MB
              (setq gc-cons-percentage 0.1)))
  ;; During startup, minimize overhead
  (setq gc-cons-threshold most-positive-fixnum)
  (setq file-name-handler-alist nil))

;; Do not load default system-wide init files
(setq inhibit-default-init t)
#+end_src

*** Benchmark & Startup Diagnostic Timer
To keep track of startup performance over time, we display a concise summary in
the =*Messages*= buffer upon launch. Inspired by [[https://docs.doomemacs.org/][Doom Emacs]], this logs the total
startup duration and the number of garbage collection passes executed during
boot.

#+begin_src emacs-lisp
(add-hook 'emacs-startup-hook
          (lambda ()
            (let ((elapsed (float-time (time-subtract (current-time) before-init-time))))
              (message "Emacs booted in %.2fs (%d GC runs)." elapsed gcs-done))))
#+end_src

*** Custom File & Local Overrides
The Emacs Customize system utilizes the value of the variable ~custom-file~ to
write its customization forms. If the value of this variable is not defined, it
will write the settings to ~user-init-file~ (=init.el=). To prevent Emacs from
cluttering =init.el=, we redirect ~custom-file~ inside =early-init.el=.

#+begin_src emacs-lisp :tangle early-init.el
(setq custom-file (expand-file-name "custom.el" user-emacs-directory))
#+end_src

In =init.el=, we load ~custom.el~ along with a ~local.el~ file for
machine-specific settings (e.g., work emails, private keys) that should not be
tracked in Git. We also start the Emacs server once initialization completes.

#+begin_src emacs-lisp
(require 'server)

(add-hook 'after-init-hook
          (lambda ()
            (let ((local-file (expand-file-name "local.el" user-emacs-directory)))
              (when (file-exists-p local-file)
                (load-file local-file))
              (when (file-exists-p custom-file)
                (load-file custom-file))
              (unless (server-running-p)
                (server-start)))))
#+end_src

** Package Management
*** Initial Package Setup
Starting with Emacs 29, [[https://github.com/jwiegley/use-package][use-package]] is bundled with Emacs as an [[https://lists.gnu.org/archive/html/emacs-devel/2022-12/msg00261.html][official part of
the distribution]]. However, this configuration retains the traditional bootstrap
steps to preserve compatibility with older Emacs versions.

We also ensure GNU ELPA signing keys stay updated via ~gnu-elpa-keyring-update~
and allow ~package.el~ to upgrade built-in libraries. Emacs disables built-in
library upgrades by default to preserve base-system stability, but modern
packages frequently require newer versions of shared dependencies than what
Emacs ships with. The core package compatibility layer applies the relevant
minimum versions before the rest of the package configuration is loaded.

#+begin_src emacs-lisp
(require 'package)
(setq package-enable-at-startup nil)

;; Allow package.el to upgrade built-in packages when newer external versions
;; are required for compatibility with modern packages.
(setq package-install-upgrade-built-in t)

;; Configure package directories to use user's elpa directory
(setq package-user-dir (expand-file-name "elpa" user-emacs-directory))
(add-to-list 'package-directory-list package-user-dir)

(setq package-archives
      '(("MELPA Stable"   . "https://stable.melpa.org/packages/")
        ("GNU ELPA"       . "https://elpa.gnu.org/packages/")
        ("MELPA Unstable" . "https://melpa.org/packages/")
        ("Non-GNU"        . "https://elpa.nongnu.org/nongnu/")
        ("GNU-devel"      . "https://elpa.gnu.org/devel/")
        ("JCS-ELPA"       . "https://jcs-emacs.github.io/jcs-elpa/packages/"))

      package-archive-priorities
      '(("MELPA Stable"   . 25)
        ("GNU ELPA"       . 20)
        ("MELPA Unstable" . 15)
        ("Non-GNU"        . 10)
        ("GNU-devel"      . 5)
        ("JCS-ELPA"       . 0)))

(package-initialize)

(unless package-archive-contents
  (package-refresh-contents))

(unless (package-installed-p 'use-package)
  (package-refresh-contents)
  (package-install 'use-package))

(unless (package-installed-p 'gnu-elpa-keyring-update)
  (package-install 'gnu-elpa-keyring-update))

(require 'gnu-elpa-keyring-update)
(require 'use-package)
(setq use-package-always-ensure t)
(setq use-package-compute-statistics t)
#+end_src

*** Package VC Helpers
Modern Emacs versions (29+) support direct package installation from Version
Control (VC) repositories via ~package-vc-install~.

The ~when (fboundp ...)~ below guard ensures this code only runs if the
~package-vc~ extension is available, maintaining compatibility with older or
minimal Emacs setups.

Because standard ~package-installed-p~ doesn't always recognize manually cloned
or VC-installed packages, we define a helper function to verify package
directory existence on disk.

#+begin_src emacs-lisp
(declare-function cfg-core/package-vc-installed-p nil)

(when (fboundp 'package-vc-install)
  (defun cfg-core/package-vc-installed-p (package &optional repo-name)
    "Check whether PACKAGE is installed on disk or via package-vc.
REPO-NAME is an optional repository directory name if it differs from PACKAGE."
    (let* ((installed-p (package-installed-p package))
           (feature-p (featurep package))
           (pkg-name (format "%s" package))
           (actual-repo-name (or repo-name pkg-name))
           (pkg-dir (expand-file-name pkg-name package-user-dir))
           (repo-dir (expand-file-name actual-repo-name package-user-dir))
           (dir-exists-p (or (file-directory-p pkg-dir)
                             (and repo-name (file-directory-p repo-dir)))))
      (and (or installed-p feature-p) dir-exists-p))))
#+end_src

* TRAMP Debugging
If you experience slowdowns, lockups, or unexpected behavior when using TRAMP
(Transparent Remote Access, Multiple Protocols), the problem may be caused by
custom functions, third-party packages, or complex configurations interacting
with remote files.

Enabling verbose TRAMP logging can help you pinpoint the source of these issues.
With high verbosity, all TRAMP operations and protocol dialogs will be recorded
in detail. Review the output in the *tramp/debug* buffer to identify problematic
commands, bottlenecks, or failing operations.

Notes:
- Logging is disabled by default to avoid performance overhead.
- Only enable when actively debugging TRAMP issues.
- Remember to disable (or lower) verbosity after troubleshooting.

** Configuration End Markers (Lisp Integrity)
These lines mark the end of each configuration file.
When Emacs loads .el files, it reads Lisp code line by line. If the file ends
abruptly (for example, with an open parenthesis or unfinished expression),
Emacs will stop with an error such as "End of file during parsing."

Including a clear end marker like this helps avoid confusion and ensures that
the file is read completely and correctly:

#+begin_src emacs-lisp
;;; init.el ends here
#+end_src

#+begin_src emacs-lisp :tangle early-init.el
;;; early-init.el ends here
#+end_src

These markers are a long-standing Emacs convention. They help maintain code
integrity and make it immediately obvious that the file ends where it should.
